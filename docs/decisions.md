## D-001 · 六轴改四轴

**日期** 2026-10-24

**原来的六轴**：共鸣 / 张力 / 玩心 / 信任 / 专注 / 亲密

**怎么发现的**：拿 8 个默认角色的数据算相关系数。

```
共鸣 ↔ 亲密    r =  0.98
张力 ↔ 亲密    r = -0.97
共鸣 ↔ 张力    r = -0.95
信任 ↔ 亲密    r =  0.85
玩心 ↔ 专注    r = -0.83
```

**结论**：六个轴实际只有 **2 个独立维度**（「亲近 ↔ 尖锐」和「认真 ↔ 玩闹」）。剩下的四个是这两个的组合投影。雷达图画成六边形只是让它看起来更丰富。

**为什么会产生共线**：这 8 个角色的六维是**一个人凭印象填的**。心里先有「Grok 是个刺头」，然后把六个轴都按那个印象调 —— 当然共线。

**改法**：

| 保留 | 覆盖 | 依据 |
|---|---|---|
| 共鸣 | 原共鸣 + 亲密（0.7/0.3 加权） | 「先接情绪」是说话方式，不是关系 |
| 锐度 | 原张力 | 改成正向词，好转述 |
| 幽默 | 原玩心 | 通用词 |
| 严谨 | 原专注 | 通用词 |

**删掉的**：`信任`、`亲密` → 它们是**关系**不是**性格**，进了动态层。

**否掉的方案**：合并成 2 轴。雷达图会退化成一条线 + 一个垂直分量，用户看不出性格差异。

## D-002 · 动态值和静态值分开，动态不画进雷达

**日期** 2026-10-24

**问题**：如果「心情」和「共鸣」画在同一张图上，用户会以为**性格在变**。

**分层**：

| 层 | 内容 | 变化速度 | 谁定 |
|---|---|---|---|
| 静态四轴 | 性格底色 | 一年不变 | 人设文件 / 手动调 |
| 动态三轴 | 心情 / 亲近 / 记忆活性 | 一小时变三次 | 系统实时算 |

**展示**：静态四轴画雷达图；动态三轴用三条进度条放在雷达下面。

**为什么动态值不能由用户调**：如果用户能直接设「我现在很生气」，那它就变成了一个开关，不是状态。

## D-003 · 性格漂移用「累积经历」而不是「实时改值」

**日期** 2026-10-24

**要解决的问题**：静态性格如果永远不变，聊三个月和第一天没区别，就没有养成感。但直接改 `axes` 又会让「人设文件」的承诺失效。

**方案**：

```ts
baseAxes   // 人设决定的锚点，永不修改
drift      // 累积偏移，±10 封顶
exp        // 经历日志（被夸 N 次 / 被怼 N 次 / 冷落 N 小时）
```

表现值 = `clamp(baseAxes + drift)`。

**为什么是每天结算一次，不是每次互动**：
每次改的话，用户夸两句就发现「锐度从 55 掉到 53」，会觉得这角色没原则。每天结算 = 单次看不见，一个月后回头看确实变了。

**为什么封顶 ±10**：不封顶的话聊三个月她就变成另一个人了。

**否掉的方案**：漂移直接改 `axes`。那样「改人设文件」和「相处」会互相覆盖，分不清哪个起作用。

## D-004 · 一个凭据 ≠ 一个模型

**日期** 2026-10-24

**原来的实现**：

```ts
activeCredential()  // 永远取第一条
req = { model: agent.model, baseUrl: cred.baseUrl, apiKey: cred.apiKey }
```

**问题**：切到 Claude 时，程序拿着 `claude-sonnet-4.6` 去请求 `api.deepseek.com`。报错还算好的 —— 更糟的是某些中转站会返回一个 DeepSeek 的模型假装是 Claude。

**改法**：

```ts
ApiCredential { id, label, baseUrl, apiKey, models: RemoteModel[] }
Persona { model, credentialId? }
```

**为什么凭据要带模型列表**：中转站一个 Key 能出几十个模型。凭据必须知道「我能提供什么」，否则选模型时无法过滤。

**未绑定凭据时**：按模型前缀猜（`claude-*` → Anthropic，`deepseek-*` → DeepSeek）。

## D-005 · prompt 里不给「该这样做」的例子

**日期** 2026-10-24

**踩过的坑**：为了说明「打招呼就回应打招呼」，我写：

```
「你好」「深夜好」就是招呼，不要拿它当话题引子
```

**结果模型每次开场都说「深夜好」** —— 它不理解「这是例子」，只看到「这个位置该出现的东西长这样」。

**规则**：

| 类型 | 给不给例子 | 为什么 |
|---|---|---|
| 「不要做 X」 | ✅ 给具体措辞 | 它不会去做，给了更明确 |
| 「该这样做 X」 | ❌ **不给** | 会照抄成模板 |

## D-006 · 「没有」和「空的」是两回事

**日期** 2026-10-24

**踩过两次**：

**第一次**：`freshThreads()` 只建了 `group`，其他会话是 `undefined` → 切到私聊时 `messages.forEach` 崩 → 聊天区离线。

**第二次**：`clearThreads()` 用 `removeItem` → 下次 `loadThreads()` 返回 `null` → 调用方判定「从没存过」→ **加载示例数据，Rust 对话复活**。

**规则**：

```ts
null        // 从没存过 → 可以用示例数据
{} / []     // 用户清过了 → 必须保持空
```

**具体做法**：`clearThreads()` 写空存档 `{v, threads: {}}`，不是删除 key。

## D-008 · 崩溃分层：能局部坏的，绝不整体死

**日期** 2026-10-23

**三层**：

```
ErrorBoundary        顶层，只兜「整个应用崩了」
  └ PanelBoundary    每栏一个，坏一栏不影响其他三栏
      └ BlockBoundary 每个功能块一个，12 个
```

**为什么 `BlockBoundary` 健康时渲染 `<Fragment key={attempt}>`**：零额外 DOM 节点，不影响布局。

**验证过的真实案例**：`freshThreads()` 的 `undefined.forEach` → **只有聊天区变成「模块离线」**，左栏会话列表、右栏上帝视角、控制台全部正常。

## D-009 · 上下文窗口：服务端报的 > 任何文档 > 我的估计

**日期** 2026-10-24

**级联顺序**：① 服务端 `context_length` → ② 用户覆盖 → ③ 本地字典 → ④ 名字里的显式数字（`128k`）→ ⑤ 前缀兜底 → ⑥ 128k 默认。

## D-011 · 数据必须有文件留底

**日期** 2026-10-24

**原则**：**localStorage 只是缓存，不是档案。** 所有用户数据必须能落到磁盘上的文件。

**为什么**：

**① localStorage 会消失，而且原因不可控**

| 原因 | 用户看到的现象 |
|---|---|
| 换浏览器 / 换 Electron 版本 | 「我的角色呢？」 |
| 清浏览器数据 | 全没了 |
| `file://` 换成 `http://` | origin 变了，另一份库 |
| 隐私模式 | 关窗口就没了 |
| 磁盘满 / 配额超 | 静默写不进去 |

**② 同一份数据在网页和桌面版是分开的**

```
Chrome         →  %LOCALAPPDATA%\Google\Chrome\User Data\...\Local Storage\
Electron       →  %APPDATA%\3WhalesSpace\Local Storage\
```

**origin 相同也没用** —— localStorage 按「浏览器进程 + origin」隔离。

**③ 用户的东西是用户的**

角色档案、对话记录、配的 API、攒下的动态状态 —— 这些是用户花时间弄出来的。**不能因为换个入口打开就没了。**

---

### 具体做法

**Electron 里自动留底**：

```
%APPDATA%\3WhalesSpace\data\
  current.json           每次改动后覆盖写
  backup-2026-10-24.json 每天一份，保留最近 14 天
```

**浏览器里手动导出**：

设置 → 本地数据 → 导出全部数据 → 下载一个 JSON

**导入**：选文件 → 校验 `version` → 合并或覆盖 → 重载

---

### 不做什么

**不做云同步。** 这是本地优先的应用，数据不出这台机器。

**不做加密。** 加密需要一个密钥，而密钥存哪又是个问题。**明文+明确告知**比假的安全感好。

---

### 判断标准

**任何时候，用户应该能回答**：

> 「如果我换台电脑，我的角色和对话怎么带过去？」

**答案不能是「带不过去」。**

## D-012 · 应用的 origin 必须恒定，不能随端口漂移

**日期**：2026-10-24

### 问题

生产模式起本地 HTTP 服务加载 `dist/`，端口序列是 `[1420, 1421, 1422, 1423, 1424]`。1420 被占（比如 dev server 开着，或上一次的进程还没退干净）就静默退到 1421。

看起来只是换了个端口，实际后果是：

- `http://127.0.0.1:1420` 和 `http://127.0.0.1:1421` 是**两个不同的 origin**
- localStorage 按 origin 隔离 → **同一台机器上出现两套数据**
- 而两边都往同一个 `current.json` 里写 → **互相覆盖**

用户看到的现象是「我的角色怎么没了」。其实是角色被分到另一个 origin 里，跟这边没有关系。

### 决定

**生产模式改用自定义协议，origin 恒为 `app://3whales`。**

`app://3whales` 跟端口、跟 `dist/` 目录、跟打包路径全都无关，永远不会变。

```js
// main.cjs，必须在 app ready 之前
protocol.registerSchemesAsPrivileged([
  { scheme: "app", privileges: {
      standard: true,        // 有正常 origin，不是 opaque
      secure: true,          // 算安全上下文：crypto / clipboard / fetch 正常
      supportFetchAPI: true, stream: true, codeCache: true,
  } },
]);
```

端口静态服务的代码保留，只作为 `protocol.handle` 注册失败时的退路。

### 附带的两条规矩

**① 排查数据问题，第一眼看 origin。** 主进程在 `did-finish-load` 里打 `url` / `origin` / `localStorage` 三项。

> 注意：必须用 `webContents.executeJavaScript("location.origin")` 在渲染进程里问。
> Node 的 `new URL("app://...").origin` 返回 `"null"` —— 那是 Node 只把
> http/https/ws/wss/ftp/file 当特殊 scheme 的限制，跟 Chromium 里实际生效的
> origin 无关。照它排错会被带偏。

**② 必须单实例锁。** 两个窗口各在内存里持有一份完整状态，又都写同一个 `current.json`，后保存的盖掉前一个。双击两次图标就会触发，而且极难复现（取决于谁最后保存）。第二个实例直接退掉，把已有窗口叫到前面。

### 验证方式

```
[electron] 生产模式协议: app://3whales/
[electron] url = app://3whales/
[electron] origin = app://3whales
[electron] localStorage = ok
```

实测：清空 `Local Storage` 目录后启动，数据由 `current.json` 自动补回（`D-011` 的恢复逻辑），长度逐字段一致。

### 一个调试陷阱：LevelDB 是异步落盘的

手动改过 `localStorage`（删 key、改值）之后**立刻 `Stop-Process -Force`**，改动会丢 —— Chromium 的 LevelDB 还没 flush 到磁盘。

我第一次清测试残留就是这么翻车的：`removeItem` 之后马上强杀，重启发现凭据又回来了。

规矩：

- 改完 `localStorage`，等几秒，或者走一遍 `window.desktop.persist()` 把状态同步进文件
- 退出用 `window.desktop.close()`（正常关闭），不要硬杀
- 排查「改了又变回去」时，先怀疑是不是没 flush，而不是代码写错了

正常使用不会碰到：文件的写入是主进程 `fs.writeFileSync`，比 LevelDB 直接；而且 5 秒定时器一到就落盘了。

（2026-10-28 从「2.5 秒防抖」改成「5 秒定时器」—— 原因见 D-022。）

### 为什么不做云同步 / 不做加密

见 `D-011`。这里只强调一点：**origin 稳定是「数据不会莫名消失」的地基**。地基不稳，上层的备份、恢复、导出都是给一个会移动的靶子打补丁。

## D-013 · 换血：协议、身份、目录全部改名，数据靠两重保险活下来

**日期**：2026-10-24

> ⚠️ **本条取代 `D-012` 里的 `app://3whales`**。D-012 的原则（origin 必须恒定）依然成立，
> 只是那个恒定的值换成了 `app://habitat`。

### 背景

软件从「我和两条小鲸鱼的互动平台」长成了「多角色智能体生态系统」。
「三鲸」这个名字变成了枷锁 —— 它暗示这软件只装得下三个角色，而它现在住着 8 个，
用户可能装 20 个。

定名 **《生境 / Habitat》** 之后，主人要求**从底到外彻底换血，不留任何旧包袱**。

### 改了什么

| 层 | 旧 | 新 |
|---|---|---|
| 协议 host | `app://3whales` | **`app://habitat`** |
| `package.json` name | `three-whales-space` | `habitat` |
| appId | `com.threewhales.space` | `com.goldenmoon.habitat` |
| productName | `3WhalesSpace` | `Habitat` |
| 打包产物 | `三鲸空间-0.1.0.exe` | `生境-0.1.0.exe` |
| 用户数据目录 | `%APPDATA%\three-whales-space` | `%APPDATA%\habitat` |
| 项目目录 | `D:\3Whales_App` | `D:\Habitat_App` |

`scheme` 本身仍是 `"app"`，改的只是 host。

### 数据怎么保住的（这是本条的重点）

换 origin = localStorage 变空。三步走：

**① 先导出，再动代码**
`scripts/export-before-migration.mjs` 通过 CDP 从运行中的 app 里把**全部 `3w:*` 键**
读出来写成 JSON（`D:\Habitat_Backup\localstorage-*.json`）。
同时把整个 `%APPDATA%\three-whales-space` 复制一份（226 文件 / 20.7 MB）作为第二重保险。

**② 改完代码，先启动一次确认新 userData 路径**
Electron 的 userData = `%APPDATA%\<name>`，所以改名后路径变成 `%APPDATA%\habitat`。
必须先启动一次让目录出现，否则会往错的地方找数据。

**③ 用旧 `current.json` 覆盖新目录的，并清掉新 origin 的 localStorage**
这一步是关键，容易漏：

- 第一次启动新版本时，`bootstrapRestore` 读不到 `current.json`（新目录是空的）
  → 用默认值 → **autosave 立刻写了一份默认数据的 `current.json`**（11 KB）
- 如果直接往里灌旧数据，`bootstrapRestore` 的「填空不覆盖」会判定「本地已有值」而跳过
- 所以：**覆盖 `data/current.json` + 删掉 `Local Storage` 目录**，让本地真的是空的

### 踩到的坑

**① 目录 rename 失败** —— `Rename-Item` 和 `cmd move` 都报
「being used by another process」。查不到具体占用者（可能是 DSH 的文件监视或系统索引）。
→ 改用 `robocopy` 复制。**9.5 GB 里真正的代码只有 3 MB**，其余是 Rust 工具链缓存
（6.6 GB）、npm 缓存、打包产物；排除这些后只搬 524 MB，1.8 秒完成。

**② 旧目录删不掉** —— 内容全部清空了（0 文件），只剩一个空壳被句柄锁着。
重启后可以删。这不影响使用。

**③ `%APPDATA%\habitat` 和 `\Habitat` 看着像两个目录** —— 其实同一个
（`Get-Item` 的 `FullName` 一致）。Windows 大小写不敏感，别被吓到。

### 给以后的维护者

**换 origin 之前，必须做的事**：

1. 跑 `node scripts/export-before-migration.mjs`（app 要用 `DESKTOP_DEBUG_PORT=9222` 启动）
2. 备份整个 userData 目录
3. 改完之后，**用旧 `current.json` 覆盖新目录的，并清掉新 origin 的 Local Storage**
4. 启动验证 `origin` 和每个键的长度都对得上

**救急工具**：`node scripts/restore-from-backup.mjs`
无条件把备份灌回当前 origin（不依赖「填空不覆盖」那套判断），适合「本地已有脏数据」的场合。

**这次真正的英雄是 `D-011` 的文件留底** —— 没有 `current.json`，换协议就等于数据全灭。

## D-014 · API Key 用系统密钥库加密，不再明文落盘

**日期**：2026-10-24

> 部分取代 `D-011` 里「不做加密」那一条。

### 起因

主人问：「Windows 没有加密方法吗？」

有。我之前的回答「纯前端没有安全的密钥存储」只对**浏览器**成立。桌面端从一开始就有
`safeStorage`，是我把「跨平台统一」看得太重，牺牲了桌面端本该有的保护。

### 用什么

Electron 的 `safeStorage`，各平台底层：

| 平台 | 后端 |
|---|---|
| Windows | DPAPI（`CryptProtectData`，从当前用户登录凭据派生密钥） |
| macOS | Keychain（独立加密存储；T2 / Apple Silicon 走 Secure Enclave） |
| Linux | libsecret（gnome-keyring / KWallet） |

**一行代码，三端通吃。**

### 威胁模型（这是决定值不值得做的关键）

| 场景 | 能防吗 |
|---|---|
| `current.json` 被拷走 / 备份传到网上 | **能** —— 换个用户或机器就是乱码 |
| 别的 Windows 账户登录这台机器 | **能** |
| 硬盘被拆下来读 | **能** |
| **同一用户账户下**运行的其他程序 | **不能**（DPAPI 解密不要额外凭据） |
| 有人能远程控制桌面 | **不能** |

后两条是所有「免密加密」的共同边界：**要让本人不输密码就能解密，密钥就必须能从他的
登录凭据推出来。** 想防同用户的其他程序，只有「每次启动输密码」一条路，那是另一回事。

### 实现：为什么是「启动时解密进缓存」

`loadCredentials()` 被几十处**同步**调用（渲染、`resolveCredential`、UI）。
把它改成 `Promise` 会传染整条调用链。

所以：

1. `main.tsx` 的 `boot()` 里，在 `bootstrapRestore()` 之后 `await hydrateCredentials()`
2. `hydrateCredentials()` 把磁盘上的 `enc:v1:...` 解成明文，放进模块级 `cache`
3. `loadCredentials()` 有缓存就返回缓存（同步）
4. `saveCredentials()` 更新缓存 + **异步**加密写回磁盘

**只有一处是异步的**，其余调用方一行不用改。

### 数据格式

```
3w:credentials 里的 apiKey 字段：
  "enc:v1:<base64>"   ← 加密（桌面端）
  "sk-xxxx"           ← 明文（浏览器预览，或加密不可用）
```

带前缀是为了**兼容存量**：`hydrateCredentials()` 发现是明文就顺手加密重写一次。
实测三套凭据在首次启动时全部自动迁移完毕。

### 导出策略

磁盘上是密文，直接导出就是「换机器打不开的废数据」。所以 `collectData()` 加了 `secrets` 参数：

| 值 | 行为 | 用在哪 |
|---|---|---|
| `"strip"`（**默认**） | 整个 `3w:credentials` 不导出 | 「导出全部数据」按钮 |
| `"plain"` | 解密成明文写进去 | 明确要「换机恢复」时 |
| `"encrypted"` | 原样密文 | **自动存档**（`autosaveNative`） |

**自动存档必须用 `encrypted`** —— 否则每次定时落盘都会把凭据抹掉。

### 解不开的时候

换机器、重装系统、系统重置密钥 —— `cryptoDecrypt` 返回 `null`，
`hydrateCredentials()` 把该套 `apiKey` 置空，`main.tsx` 打一条 warn。
UI 上那套凭据变成「需要重填」，而不是静默失败。

### 教训

**别用「跨平台一致」当不做安全设计的理由。** 正确的做法是「能用就用最好的，用不了
就明确标注降级」——这正是浏览器预览时那句警告改成动态文案的原因。

## D-015 · 解析引擎从四级砍到两级，删掉 L3 和 L4

**日期**：2026-10-24

### 判断

主人先问：「很多用户电脑里可能没有 Ollama，下载很难」——
然后说：「把 L4 也砍了得了，毕竟我都不知道 L4 如何实现效果」。

第二句是决定性的。**连设计者都说不清它跑起来什么样，它就不该待在产品里。**

### 砍掉的两级

| 级别 | 原来的设想 | 为什么砍 |
|---|---|---|
| **L3 端侧 WebGPU** | 浏览器里跑 Qwen2.5-0.5B，隐私兜底 | **0.5B 模型做语义判断约等于随机**，精度不如 15 条正则，门槛却要 WebGPU + 380 MB。Electron 里 WebGPU 支持很不稳定（实测这台机器要么 unavailable 要么卡在 probing） |
| **L4 本地 Ollama** | 7B–14B 本地跑，隐私和精度兼顾 | 要装 Ollama + 下 2–14 GB 模型。对「读一段文字输出四个数」这种任务，门槛荒谬。而且它的「测试连接」按钮从头到尾就是一个 setTimeout 播动画 |

### 留下的两级

```
L1 内置正则   零配置、本地、精度中、< 1 ms
L2 云端 API   已有凭据、精度高、出网、1.2–3 s
```

**「本地 + 高精度」这一格空着了。** 这是有意的取舍：宁可承认它空着，也不放一个假选项进去。

### 顺带修的：L2 不再要求重复填 Key

以前「API 接入」和「解析引擎」各维护一套 Key，而后者那个「保存」按钮只把输入变成掩码，**根本没存**。

现在 L2 直接读 `3w:credentials`：

- `statusOf(2)` 用 `hasCloudCredential()` 判断，不再看那个假的 `keySet`
- UI 列出你配的几套凭据，点一下选中
- 模型从该凭据的**真实模型列表**里选（以前是硬编码的 `deepseek-v3.2`）
- 没配凭据时显示「去配置 API →」，不让人在这儿再填一遍

### 迁移

旧存档里的 `level3` / `level4` 和 `chain: [4,3,2,1]` 在读档时被剔掉：

```ts
const { level3: _d3, level4: _d4, ...saved } = raw;  // 显式剔，防 ...saved 带回
chain: (saved.chain ?? DEFAULT.chain).filter(l => l === 1 || l === 2),
active: saved.active === 1 || saved.active === 2 ? saved.active : (hasCloudCredential() ? 2 : 1),
```

### 下一步（如果要做）

**加强 L1**，而不是再找一个 L4：

- 否定词检测（不要 / 别 / 不许 / 少一点）
- 程度词加权（很 / 特别 / 有点 / 稍微）
- 句子级正负抵消

修完的 L1 比 0.5B 端侧模型准，而且零门槛。

### 教训

**界面上每一个「待配置」都在向用户承诺：配一下就能用。**
如果那个配置的代价是装几百 MB 的软件、下几 GB 的模型，那不叫待配置——那叫不该出现在这里。

## D-016 · 人格解析真正接上了：L1 加强 + L2 通 LLM

**日期**：2026-10-24

### 背景

解析引擎之前是「仪表盘接好了，但发动机没装」：
`analyzePersonaConfig()` 写得很完整（15 条规则、1/√n 折扣、±28 封顶、带 snippet 证据），
但**从来没被调用过**。角色创建靠手动拖四个滑块。

这一轮把它真接上了，并且修了 L1 的两个已知缺陷。

### L1 的修复

**① 否定句**

以前「不要撒娇」会同时命中 `撒娇`(+10) 和 `不要撒娇`(-10)，两笔抵消 —— 等于没说。

现在：先看命中位置**之前、同一句内**有没有否定词，再决定这一笔往哪边。

```ts
const net = positive - negated;   // 净正向次数
if (net === 0) continue;          // 正负抵平 → 这条规则不表态
const amount = sign * rule.amount * scale;
```

注意最后一行的 `rule.amount` **不能取绝对值** —— 有些规则天生是负向的
（`不要寒暄` 定义成 -8），取绝对值等于把它理解反了。

**② 标点断句**

「不要寒暄，直接给结果」里那个「不要」管的是寒暄，管不到逗号后面的半句。
否定窗口遇到标点就截断，否则后半句会被误判成否定，整条规则失效。

**③ 程度词**

`非常黏人` (+20) 和 `有点黏人` (+8) 不再同分：

| 词 | 倍率 |
|---|---|
| 最 / 极 / 非常 / 特别 / 很 | ×1.45 |
| 有点 / 有些 / 稍微 / 偶尔 | ×0.6 |

验证脚本：`npm run test:l1`（或 `node scripts/test-l1.mjs`）

### L2 的接入

新增 `src/lib/personaAnalyze.ts`：

- `analyzeWithRules()` —— L1，纯正则，< 1 ms
- `analyzeWithLlm()` —— L2，调 LLM 返回 JSON
- `analyzePersonaText()` —— 统一入口，UI 无差别切换

凭据查找三级兜底：指定的 → 按模型名反查 → **第一套有 key 的**。
（第三级是必须的：UI 调用时不传参数，少了它就会误报「没有可用凭据」。）

结果呈现：每条 Δ 都带 `snippet` 原文片段，UI 里能逐条看到「凭什么」。
Δ 是**叠到现有滑块上**的，不覆盖 —— 用户手拖过的值不该被一键抹掉。

### 踩到的坑：deepseek-flash 会静默返回空字符串

这是本轮最有价值的发现。

给 LLM 的 prompt 里有这么一句：

> evidence 必须是从原文原样摘的短句，找不到就留空字符串。

**模型直接返回 0 字符。不报错、不拒绝、不解释。** 看起来像网络故障。

二分测试结果：

| prompt 形态 | 回复 |
|---|---|
| 只给 axes 格式示例 | 42 字符，正确 |
| 给完整格式示例（含 evidence） | 118 字符，正确 |
| **只提 evidence 要求、不给示例** | **0 字符** |
| 加轴定义 / 长文本 / 三引号包裹 | 都正常 |
| **加「必须原样摘」那句** | **0 字符** |

结论：**不是长度问题，是那一条具体指令它处理不了。**

去掉之后，模型照样会填 evidence（而且填的就是原文片段）——
**格式示例已经把意图说明白了，不需要再写一条硬要求。**

同时加了兜底：第一次返回空 → 换极简 prompt（只要 axes）再试一次 →
还空就报错「两次都返回空，换个大点的模型或者改用 L1」，而不是静默失败。

### 教训

**LLM 的 prompt 不是「写得越全越好」。**

给模型 10 条要求，它可能一条都做不到 —— 而且**不告诉你**。
给一个格式示例，它自己就懂了。

这条同样适用于 `D-005`（prompt 里不给「该这样做」的例子）：
那里是「例子会污染输出」，这里是「要求会压垮输出」。两个方向，同一个道理——
**别替模型把话说完。**

### 后续：让「内容一致」就返回一致结果（D-016 补充）

主人问：「那不如让解析的那个 ai，内容如果一致就返回相同结果呢？」

**对，这才是正解。** 前面一直在纠结「怎么让 AI 稳定」，方向错了 ——
该做的是「内容一样就别重新问」。

#### 规范化缓存 key

```ts
function normalizeForCache(text) {
  return text
    .replace(/[\s\u3000\u00a0]+/g, "")        // 所有空白
    .replace(/[，。、；：！？…—·,.;:!?]/g, "") // 中英文标点
    .replace(/[「」『』“”‘’"'（）()【】\[\]《》<>]/g, ""); // 引号括号
}
```

缓存 key 用**规范化后**的文本，所以：
「……敢拆我的台。」「……敢拆我的台」「……敢拆我的台,」会被视为同一份人格。

实测四种写法（原始 / 去句号 / 半角逗号加空格 / 全去标点）→ **结果逐位相同，0.8 s 返回**。

#### 两个必须修的 bug（都是这次暴露的）

**① `extractJson` 太脆弱 —— 一个裸引号就让整条解析作废**

原实现只做「取第一个 `{` 到最后一个 `}`」再 `JSON.parse`。
模型在 evidence 的字符串里写一个未转义的 `"` 或换行，整条 JSON 就非法 ——
**而 axes 明明是对的**，用户看到的却是「没返回有效结果」。

改成三级策略：

1. 原样解析
2. 清掉字符串里的裸控制字符再解析
3. **放弃 evidence，正则只抠 `"axes":{...}` 里的四个数**

第三级是保底：拿不到依据也要拿到数值，因为数值才是用户要的东西。
另外，解析失败时也走一次极简 prompt 重试（以前只在「空回复」时重试）。

**② 冷启动后的第一个请求必失败**

实测：每次应用启动后第一次点「解析四轴」都失败，第二次就正常 ——
主 prompt 和极简兜底**都返回空**，像连接池/TLS 还在建。

修法：每次采样内部再重试 3 轮（间隔 1.2 s）。
**不能「试一次就放弃」** —— 否则用户从此处开的第一个解析永远失败。

#### 最终验证

```
1 原始        OK  0.8s  60,70,60,55
2 去末尾句号   OK  0.8s  60,70,60,55
3 半角逗号+空格 OK  0.8s  60,70,60,55
4 全去标点     OK  0.8s  60,70,60,55
```

### 关于「LLM 结果不稳定」的最终结论

**修不掉，也不该假装修掉。**

试过并失败的方案：

| 方案 | 结果 |
|---|---|
| `temperature: 0` | 同文本两次仍差 5 分 |
| 量化到 5 的倍数 | 差额缩到 0–5，没归零 |
| 采样 3 次取中位数 | **更糟**：连续调用被静默限流，3 次只成 1 次 |

所以最终的做法是：

- **缓存**解决「同样内容」的一致性（这是用户真正在意的）
- **量化到 5** 降低假精度
- **UI 明说**「模型判断有 ±5 的波动 —— 觉得不对直接拖滑块改」

**它不是测量仪，是「起点的建议」。**
四轴雷达看的是形状不是绝对值，共鸣 55 和 60 画出来的菱形几乎一样。

### 教训

**用户说「让它返回相同结果」时，说的是工程需求，不是模型能力。**

我花了三轮去调模型参数（temperature / 采样 / 量化），全都在答错题。
正确答案是加一层缓存 —— 五分钟的活。

## D-017 · 语音分三档，而且最低那档必须零配置

**日期**：2026-10-28

### 背景

做 TTS 时，第一版只做了「云端」：让用户自己填一个 OpenAI 兼容的 Base URL + Key。

用户反问：

> **「如果没有服务器呢？你不可能指望每个用户都有服务器吧」**

这句话是对的。我当时给的备选方案是 Cloudflare Workers 转发 —— **但那还是要注册、装 wrangler、部署**。对普通用户依然是门槛。

而我一直在跳过一个东西：**`speechSynthesis` 是浏览器自带的。**

### 决定

**三档，从「谁都能用」到「要好听的」：**

| 档位 | 实现 | 用户要做什么 | 声音 |
|---|---|---|---|
| **关**（默认） | —— | 无 | 只有提示音 |
| **系统** | `speechSynthesis` | **无** | 机械 |
| **云端** | OpenAI `/v1/audio/speech` | URL + Key | 好听 |

**顺序是刻意的：先让「能听」成立，再谈「好听」。**

### 为什么「系统」那一档不能删

它是**唯一一个不受任何第三方政策影响**的档位。

- OpenAI 的 `tts-1` / `tts-1-hd` / `gpt-4o-mini-tts` **2027-01-06 关停**
- 指定的替代品 `gpt-realtime-2.1-mini` **明确不支持 `/v1/audio/speech`**
- 各家服务商的条款、定价、端点都可能变

**而操作系统自带的语音引擎不会发邮件说要关停。**

### 顺带的两条

**① 不内置任何服务商，只给插口**

`Base URL + API Key + 模型名`。走 OpenAI `/v1/audio/speech` 格式 —— 那是事实标准。

已知能用的：OpenAI 官方、SiliconFlow、Fish Audio（`/compat` 层）、new-api / LiteLLM 网关。

**② 不校验 `voice`**

`voice` 有三种形态：固定枚举（`alloy`）、平台音色名（SiliconFlow）、任意 ID（Fish Audio 的 `reference_id`）。

**没法统一** —— 所以代码**填什么发什么**，一个白名单都不加。

同理，`Base URL` 支持两种填法：填到 `/v1`，或直接填完整路径（以 `/audio/speech` 结尾，那样原样使用）。

### 教训

**「让用户自己配」听起来是自由，实际是把成本转嫁给每个用户。**

而且那个成本要**每个用户重走一遍**。

**默认档必须是谁都不用做就能用的那一个。** 高级选项是给愿意折腾的人的，不是给所有人的起点。

## D-018 · 语音不自动播放

**日期**：2026-10-28

### 背景

第一版是自动播的：她回一条，就念一条。

**问题在群聊** —— 三个角色连着回，三条语音互相打断（`stopCurrent()` 会停掉上一条），**实际只能听到最后一条的前半截**。

长回复也一样：念两分钟，人早就在看下一句了。

**顺带发现**：界面上那个 🔊 按钮是假的 —— `doSpeak` 只弹一个 toast「开始朗读」，根本不念。和假日志同一类问题。

### 决定

**不自动播。每条消息旁边一个 🔊，点才念。**

- 点 → 念，再点 → 停
- 正在念 → 按钮变青 + 呼吸
- 没配语音 → 提示「设置 → 语音」
- 没正文 → 提示「这条念不了」

**同时删掉自动播** —— 恢复无条件 `playReceive(pitch)` 提示音。

### 为什么

**文字流是主，语音是按需。**

这也让「收到音」重新变成**每条消息只有一个音** —— 不会打架。

**我一度想给自动播打补丁**（群聊只念最后一条 / 超过 120 字只念第一段），但那是给错误的前提做优化。

**去掉前提，补丁就不需要了。**

### 教训

**遇到「这个功能在某些场景下很糟」时，先问「这个功能该不该存在」，再问「怎么修」。**

我提了两条规则（群聊只念最后一条、长文只念第一段），用户一句话就把整个问题拿掉了：**「那就不要自动播放了嘛」**。

## D-019 · 发送与收到分开：6 秒待发窗口

**日期**：2026-10-28

> **⚠️ 部分被 D-024 取代（同一天）**：这一条里的「6 秒后撤回 + 留壳」已经删掉。
> 「6 秒窗口」本身保留，撤回改成了**只在窗口内取回 / 删除**。
> 下面关于「为什么要有窗口」的推理仍然有效。

### 背景

原有的撤回是「立刻发 + 撤回后清理」：清掉内容，留一条「已撤回」的占位。

**但 AI 已经生成了回应。** 撤回之后 prompt 历史里出现：

```
assistant: "大白饭。你上次说想吃那个。"
           ↑ 她回了一句针对不存在的话
```

模型会以为自己主动开口说过「大白饭」—— 下一轮可能顺着编前言，或者困惑出戏。

### 决定

**「发出去」和「让她收到」拆成两件事。**

| 操作 | 结果 |
|---|---|
| **Enter** | 消息上屏（半透明 + 倒计时条 + 「待发」）。**AI 还不知道。** |
| **6 秒内再 Enter** | 立即发出 |
| **6 秒内撤回** | **直接消失**。提示「已收回 · 她没看到这条」。**不留占位。** |
| **6 秒走完** | 自动发出 |
| **6 秒后撤回** | 提示「已撤回 · **她已经看到了**」，留占位壳 |

### 撤回的两个分支（这是关键）

```ts
if (pendingSend.current?.id === id) {
  /* 待定的那条：直接删，她没看到。它从没存在过，不该留占位 */
  ...
  return;
}

/* 已发出的那条：留占位壳。历史里它还在 —— 模型看到的是
   「这里有过一句话，被撤了」，而不是「这里什么都没有」 */
```

**留占位不是为了好看，是为了防断层。**

### 提交闸门

两个真实的问题，都在「手很快」时出现：

1. **连按 Enter 绕过 6 秒** —— 两条请求间隔 1 秒
2. **上一条 AI 还没回，下一条就发** —— 两条并发

后果：回复顺序可能颠倒、`typing` 指示器提前消失。

| 限制 | 值 |
|---|---|
| 最小提交间隔 | `2000ms` |
| AI 在回时排队（`typing` 状态） | 回完 + `400ms` 自动放行 |

**这是「提交」的闸，不是「打字」的闸。** 你随时可以打字，只是它不会立刻冲出去。

### 教训

**一个看起来只是 UI 的改动（撤回），底下牵着协议的完整性。**

如果只从界面上想，答案是「撤回就删掉」。
从「模型下一轮会看到什么」想，答案变成「有些能删，有些必须留壳」。

**判断标准是：这么做之后，她下一轮看到的历史是不是自洽的。**

## D-020 · 事件流必须全真

**日期**：2026-10-28

### 背景

左栏 EVENT STREAM 原来是假的：`mock.ts` 里的 `SEED_LOGS` / `LOG_POOL`，每 3.2 秒随机抽一条播出去。

```
router›deliver ok · 4/4 ack
tts›synth chunk → 320ms · voice=jingjing
stt›partial decode 0.42s · confidence 0.94
dsh.exec›cargo clean --manifest-path src-tauri
net›retry 1/3 · upstream 502 · backoff 800ms
```

用户的质疑很直接：

> **「日志哪里为什么要全假啊，不能全真吗」**

### 决定

**全删，换成真事件。**

现在每一条都对得上软件里真的发生过的事：

```
boot › start v0.1.0
boot › restore 14 keys
data › persist 9.5KB
llm  › ok · 1840ms · 843 tok · claude-fable-5
mem  › write 1 · tag=情绪 · w=0.75
name › force「澜汐」→「月见」
doom › exec「阿澈」· 时候到了        [PIN]
```

30 个语义化入口（`log.llmOk()` / `log.memWrite()` / …），日志格式统一在 `eventLog.ts` 里。

### 为什么这不是「氛围问题」

**假 CPU 只是数字假。假日志是「虚构了一个不存在的子系统」。**

- 用户看到 `tts›synth` 会以为有语音合成 → 去找，找不到
- `router›deliver` 暗示有一个消息路由层 → 没有
- `cargo clean --manifest-path src-tauri` → **这个项目早就从 Tauri 换到 Electron 了**

**这比数字假严重得多 —— 它会教用户不信这个界面。**

### 空态

**第一次装的时候下面是空的** —— 因为确实什么都没发生。

那不丢人，那叫诚实。

### 附带的三条

| 决定 | 理由 |
|---|---|
| **`pinned` 事件置顶** | 觉醒、到期处决不该被后续日志冲走 —— 那是这段关系里的转折点 |
| **`log pause` 语义改了** | 以前是「停止生成假日志」，现在是「别把视图顶走」。**日志是事实，不该能被暂停** |
| **顺手把 `api` 命令也改真了** | 原来写死 `dsh busy` / `astrbot idle` —— 和左栏 API LINKS 同一个问题 |

### 教训

**「反正是装饰」是最容易藏假货的地方。**

因为没人会去核对装饰。而一旦装饰里有编造的系统名，**整个界面的可信度都会掉** —— 用户不会去分辨哪条真哪条假，他会整体不信。

**同一个问题在别处也犯过**：假 CPU、假 ping、假的 🔊 按钮。

**一条规矩：界面上出现的东西，必须能追溯到一行真的代码。**

## D-021 · 从对话提取记忆用本地规则，不调 LLM

**日期**：2026-10-28

### 背景

记忆系统的五个零件早就造好了：遗忘曲线、巩固算法、持久化、记忆卡 UI ——
**但没有任何地方从对话里写记忆。**

只有三个事件会写：新建角色、她自愿改名、强制改名。

所以那套幂函数衰减、间隔效应、阈值、巩固，**一直在给两条「主人把名字改了」算衰减。**

用户问得很直接：

> **「普通对话不写记忆是什么意思？那前面做的遗忘机制不就废了？」**

**是的，废了。五个零件造好了，传动轴没接上。**

### 决定

**本地规则 + 词表，不调 LLM。**

```
你说「我不吃香菜，受不了那个味」
    ↓  含第一人称 ✓ 不是纯语气 ✓ 不在问他 ✓ 长度 14 ✓ 命中偏好词
tag=偏好 · weight=0.70 · source=「他的口味」
```

### 为什么不调 LLM

| 方案 | 成本 | 质量 |
|---|---|---|
| **每句话抽一次** | **每句话多一次 API 调用** —— 慢、贵、让对话变迟钝 | 最准 |
| **本地规则** | **零成本零延迟** | 笨，会漏 |
| **混合** | 中等 | 好，但复杂 |

**关键在于：值得记的东西有形状。**

他在说自己。他说喜欢什么讨厌什么。他问了什么。
**这三件事本地规则都能认出来**，不需要模型judgment。

而代价只是**漏记** —— 漏记的后果是「她少记了一条」，不是「她记错了」。

### 宁漏不错

这个原则写在每一处判断里。

**错记一条「他说过要吃香菜」（其实说的是不吃）比漏记十条糟糕得多** ——
因为那条会进 prompt，她会一直记着错的东西，而且会主动提起。

具体体现：

- 「你觉得我今天是不是很烦」→ **不记**。有「我」也有「烦」，但那是**问他**
- 「我想哭」→ **不记**。3 字太短，规则判不出这是情绪还是随口一说
- 「我的猫昨天走了」→ **不记**。7 字，够重要但不够长 —— **这是已知的漏**

### 六道判断的顺序是有讲究的

```
① 纯语气 → ② 在问他 → ③ 有第一人称 → ④ 分 tag → ⑤ 长度 → ⑥ 纯提问
```

**长度放在分 tag 之后**，因为门槛要按 tag 定：

```
长期 / 偏好：≥4 字
其他：       ≥8 字
```

**第一版把长度放在最前面、统一用 ≥8 字**，结果把最该记的全拦了：

```
「我不吃香菜」    5 字  ← 偏好，最该记
「我叫阿野」      4 字  ← 身份，最该记
「我在杭州上班」  6 字  ← 身份，最该记
```

**最短的那几条往往最重要 —— 因为它们是事实，不是情绪。**

23 个用例，第一轮 **14 过 / 9 败**，改完 **23/23**。

### 教训

**「先写引擎再找燃料」这个顺序是反的。**

那五个零件是很漂亮的工作，但它们没有燃料的时候，
所有测试都是绿的、所有 UI 都能点、所有算法都跑得通 —— **只是结果永远是空的。**

而且这种东西很难自己发现：因为**没有任何东西会报错**。

**一个功能只要它的输入源是空的，它就不算做完了。** 哪怕代码一行不缺。

## D-022 · 落盘用定时器，不用防抖

**日期**：2026-10-28

### 背景

原来的写法是「每次变更重置一个 2.5 秒计时器」：

```ts
useEffect(() => {
  const t = setTimeout(() => autosaveNative(), 2500);
  return () => clearTimeout(t);   // ← 每次依赖变化都清掉重来
}, [threads, personas, groups, credTick, memTick]);
```

用户的追问戳中了它：

> **「为什么有 2.5 秒的改动」**

我上一轮的回答里说「断电会丢最后 2.5 秒」—— **那是错的。**

**真实行为是：每次变更都重置计时器，所以只要变更来得比 2.5 秒密，就永远不写盘。**

### 决定

**换成不会被重置的 5 秒定时器 + 脏标记。**

```ts
const dirty = useRef(false);

useEffect(() => { dirty.current = true; }, [threads, personas, groups, credTick, memTick]);

useEffect(() => {
  const tick = () => {
    if (!dirty.current) return;   // 只查一个布尔值，几乎零成本
    dirty.current = false;
    void autosaveNative();
  };
  const id = window.setInterval(tick, 5000);
  return () => { window.clearInterval(id); tick(); };
}, []);
```

**写入上限：5 秒一次。延迟上限：5 秒。两个都封住了。**

这 5 秒内进来的改动留给下一个窗口 —— 这正是想要的行为。

### 为什么这个数字是用户定的

我先给的方案是「加 15 秒上限」—— 保留防抖，但每 15 秒强制写一次。

用户说：

> **「能不能放宽时间（例如5秒），5秒一到就把前面没写入硬盘的写入硬盘，
> 当前正在回的消息就放到下一个时间段？」**

**这比我的方案干净。** 我那个是「防抖 + 兜底」，两个机制并存；
他这个是把防抖整个换掉，**只剩一个机制，语义清楚：每 5 秒收一次账。**

### 验证方式

不能只看「写了没有」—— 要测**连续改动**这个场景：

```
连续 6 秒、每秒改一次，在 t=6.0s 检查文件

localStorage : flush-test-6   （最新）
文件         : flush-test-5   （t=5 那次快照）
```

**文件在 t≈5 就写了。** 旧版防抖要等到 `t=6 + 2.5 = 8.5s` —— 那时文件里什么都没有。

### 顺带修的：记忆变更原来漏落盘

`3w:memories` 不在 `threads` 里，所以依赖数组里根本没有它。

**后果**：铭刻 / 压抑 / 提权 / 忘掉 / 删除 —— **只改 localStorage，一次文件都没写。**

做完记忆手术、关掉 app、清理 localStorage（或换机器）→ **手术白做。**

**为什么一直没暴露**：`push` 写记忆时会同时改 `threads`，**间接**触发了落盘。
只要有一处不经过 `threads`（比如记忆卡上的手术按钮），就漏了。

修法：`memoryNotes.ts` 的 `writeAll()` 是唯一写入口，在那里发 `MEMORY_CHANGED` 事件；
`App.tsx` 订阅它 bump `memTick`，计数器进依赖数组。

**一处改动覆盖所有记忆操作。**

### 教训

**「防抖」和「节流」的区别不在于写法，在于你要保哪个。**

- **防抖**保的是「别写太多次」—— 代价是**可能一直不写**
- **节流**保的是「最多等这么久」—— 代价是写入次数多一点

**我一开始选防抖，是因为只想到了「打字时别每个字都写盘」。**
但那个场景其实不存在 —— `push` 是每条消息一次，不是每个字一次。

**需求看错了，机制就选错了。**

## D-023 · 「她眼里的你」用规则改写，不调 LLM

**日期**：2026-10-28

### 背景

记忆卡里存的是**你的原话**：

```
「我不吃香菜，受不了那个味」
「我叫阿野」
```

那是「对话记录」，不是「她眼中的你」。

关系 tab 要一栏 **用她的口吻**说你是谁：

```
「他不吃香菜」
「他叫阿野」
```

### 决定

**规则化改写，不调 LLM。**

```
剥「我说过」→ 代词替换 我/咱/俺 → 他 → 超 34 字截断 → 短于 3 字丢弃
```

### 为什么不调 LLM

和 `extract.ts` 同一个理由：每次打开 tab 多一次调用，贵且慢。

**但更重要的是：这件事的难点不在"懂意思"，在措辞。**

措辞要靠人定规则，不是靠模型现场发挥。**模型每次给的句式不一样，这一栏就不可靠了** ——
今天写「他不吃香菜」，明天写「主人似乎对香菜不太能接受」。

而规则化改写有个好处：**你能预测它说什么。** 改坏了能改规则，
而不是"再抽一次看看"。

### 认了会改坏的地方

代词替换处理不了所有中文：

```
「我觉得你根本不懂我」→「他觉得你根本不懂他」   ← 通，但意思变了
```

所以加了一道显式黑名单：

```ts
const ABOUT_US = ["你根本","你不懂","你不该","我恨","我讨厌你","我不理"];
```

**这些在说「我对你的态度」，不是「你是什么样的人」。**
这类话该留在记忆卡里，不该摆进「她眼里的你」。

### 排序不是按权重

```ts
const TAG_RANK = { 长期: 0, 偏好: 1, 情绪: 2, 短期: 3 };
```

**如果纯按权重排**，一条 0.9 的「他今天很累」会把 0.7 的「他叫阿野」挤掉。

**那是错的顺序 —— 她应该先知道你是谁，再知道你今天怎么了。**

### 教训

**「AI 生成比规则好」是个默认假设，但在"短句改写"这种任务上它不成立。**

因为这里要的不是"更自然"，是**一致性**。一句话每次打开都不一样，那一栏就不像她的印象，
像每次现场编的。

## D-024 · 发出去就没有撤回

**日期**：2026-10-28

### 背景

原来的设计：6 秒内可撤回（她不知道），6 秒后也可撤回（留一个壳）。

用户看了 QQ / 微信的撤回，问了一句：

> **「在 QQ 微信里，撤回的功能就是在别人没看到消息前把消息收回，这样别人想知道都不行」**
>
> **「但是发出去后，ai 回了消息啊；我是想着发出去之后不能撤回」**

### 决定

| 阶段 | 能做什么 | 她那边 |
|---|---|---|
| **6 秒内** | **取回**（拿回来改）/ **删除**（当没发过） | **什么都没有** —— 从来没发生过 |
| **6 秒后** | 复制 · 引用 · 朗读 | 她已经看到、已经回了 |

**`handleRecall` 整个砍掉**，换成 `handleDiscardPending`（只处理待发的那条）。

`grep "撤回"` → **0 个入口**。

### 为什么这个更对

**撤回的前提是「对方还没看到」。她回了，就说明她看到了 —— 那就没有可撤回的东西。**

保留"6 秒后撤回"会制造一个逻辑上的空洞：她刚刚基于那句话回复了，
你却把话抽走 —— 要么她「回了一句针对不存在的话」（断层），
要么她知道被撤回了（那就不是撤回，是"我收回刚才的话"）。

**两种都不是撤回的本意。**

### 这比打补丁干净

上一轮我准备给撤回加一个 prompt 标记：「（他撤回了一条消息）」——
因为不留痕迹会造成断层。

**现在撤回这个动作不存在，断层就不存在，不需要补。**

**删除一个动作，比给它加三层补丁省事。**

### 代价（认了）

**发错字改不了。** 6 秒之后就是泼出去的水。

这和整个软件的调子一致：**这道疤抹不掉了。**

### 教训

**「和一个成熟产品对齐」有时意味着删掉功能，而不是加功能。**

我一直在想"怎么让撤回不出问题"（留壳、加标记、prompt 补丁），
而用户说的是"撤回这件事本身就不该存在" —— **前提错了，后面全是白工。**

## D-026 · `position: fixed` 的菜单必须 portal 到 body

**日期**：2026-10-28

### 现象

右键消息，菜单不出现。但 DOM 里查得到：

```js
document.querySelectorAll('[role=menu]').length  // 1
// 里面确实是 复制 / 引用 / 朗读
```

**元素在，尺寸也对，就是屏幕上什么都没有。**

### 原因

`ContextMenu` 用 `position: fixed` —— **但 `fixed` 不是永远对着视口。**

CSS 规范：祖先只要带 `filter` / `transform` / `perspective` / `contain`，
它就变成 `fixed` 后代的**包含块**，`fixed` 改为相对那个祖先定位。

**消息行的根节点正好带着 `filter: blur(0px)`** —— 入场动画
（`initial={{ filter: "blur(5px)" }}` → `animate={{ filter: "blur(0px)" }}`）留下的。

```
消息行（filter: blur(0px)）
  └ 菜单（position: fixed）→ 变成相对这一行定位
       └ 而这一行在 overflow-y-auto 的滚动容器里
            → 菜单被裁到看不见
```

### 决定

**`createPortal(menu, document.body)`。**

一处改动，消息右键和角色右键全部恢复 —— 因为都走同一个组件。

### 教训（测试上的）

**我第一轮只查了 DOM 就判定「通过」。**

`querySelectorAll('[role=menu]')` 有内容 → 写"✅ 菜单正常"。

**但截图里根本没有菜单。**

「DOM 里有」「CSS 算出了尺寸」「元素在视口内」—— 这三件事都成立，
它仍然可能**被祖先裁掉**。

**验证可见性的唯一可靠方式：看截图。**

后来的测试改成三条一起查：

```js
{ 在 body 下?, getBoundingClientRect 在视口内?, opacity?, 截图肉眼可见? }
```

### 顺带一个同类

同一次排查里还发现：**motion 的 `animate` 会覆写 `style` 里的同名属性。**

```tsx
<motion.div animate={{ opacity: 1 }}      // motion 写内联样式
           style={{ opacity: 0.55 }}     // 被覆盖
```

待发消息的"半透明"从来没生效过。改成 `animate={{ opacity: pending ? 0.55 : 1 }}`。

**同一个根源：以为写了就生效，但实际生效的是别人后写的那一层。**

## D-027 · 「主动」只做前台，不做托盘常驻

**决定**：她只在你开着软件的时候主动开口。不做托盘、不做后台任务、不做开机自启。

**为什么不**：

- 托盘常驻的直接后果是「怎么关都关不掉」—— 那是**投诉**，不是功能
- 而「用户随时插话、不被打断」这条诉求，本身就要求用户在场。
  用户不在，谈何插话？

**代价**：关掉软件，群就静止了。她不会在你离开的时候发消息。

这不是缺陷 —— **群本来就是会停的**。四个人的群，你不在的下午就是没消息。

## D-028 · 规则是底线，判断模型是增强

**决定**：谁说话由**本地规则**算（心情 / 亲近 / 沉默 / 记忆呼应）。
可选开启「判断模型」（一个便宜的小模型）来提高准确度。**默认关闭。**

**为什么不让模型当唯一判据**：

- 判断模型连不上 / 配错模型 / 中转站挂了 → 群直接死
- 而规则版永远是活的，只是判得粗

**为什么判断模型可能反而省钱**：

```
一次发言 ≈ 12,000 tokens
一次判断 ≈    560 tokens
→ 一次发言 = 21 次判断
```

判断能拦掉「本来不该发的那几条」，它就自己付了钱。

**硬约束**：判断模型**只做选择题，不做填空题**。
它只能从本地筛好的 3 条记忆候选里挑一条，不能自由回忆 ——
否则它会编一条记忆库里没有的事，而主模型会当真说出来。

## D-029 · `[@名字]` 用方括号，且 @ 用户不阻塞别人

**决定**：
1. 格式是 `[@名字]`，不是裸 `@名字`
2. AI `@` 了**用户** → 只记一个「在等你」的标记，**不冻结群聊**

**为什么用方括号**：正文里本来就可能出现 `@`（邮箱、代码、转述）。
`[改名:新名字]` 已经验证过这条路 —— 方括号 + prompt 约束，解析零歧义。

**为什么 @ 用户不能阻塞**：第一版设计成「@ 了你 → 全场停」，
结果是**你一走，群就死**。那是设计的锅，不是群的锅。

改成不阻塞之后：你不在 → 他们聊两句 → 意愿耗尽 → 安静。
**结果一样是安静，但理由是对的。**

另外：**@ 是稀缺品，不是驱动对话的手段**。
真实群里 @ 只有三种场景（被点名回复、这件事只有你能答、有人被晾着），
没有「我想让对话继续所以 @ 一下」。prompt 里写死了这条。

## D-030 · 「沉默」看 `spokenAt`，不看 `DynamicState.lastAt`

**决定**：`ConversationRuntime` 单独记每个人**上一次开口**的时间。

**为什么不能复用 `lastAt`**：

`lastAt` 是「这个角色最后一次有动静」——**用户发一句话，群里所有人都会被
`tick()` 一次，`lastAt` 全部变成「刚刚」**。于是「沉默加成」在对话进行中
恒为 0，AI 说完一句就再没人想接。

第一版就是这么写的，表现是「她说完一句，群突然安静了」。

**顺带修的一个同源错误**：`idleMin === Infinity ? 0` —— 用 `Infinity`
表示「从没开过口 = 最想说」，公式里却把它算成零。语义正好反了。

**这两条说明一件事**：中文变量名 `沉默` / `意愿` 很容易让人以为自己写对了，
而真正的错误在「这个字段到底代表什么」。`lastAt` 和「她最后说话」
在自然语言里都能叫「上次」，在数据上是两件事。
