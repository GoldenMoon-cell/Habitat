## 零前 · ⚖ 物理法则（最优先）

> **2026-11-03 定。这条和后面任何一条冲突时，以这条为准。**
> 后面的几节是讨论过程，有些结论已经被这条覆盖 —— 我不删它们，
> 因为「为什么改」比「改成什么」有用。

### 法则只有一条

> **重的沉下去，轻的浮起来。**

大而实的东西沉在海底。小而虚的东西浮在水面。
**记性也是这样。**

### 由它推出的全部

```
被忘记  →  变轻  →  上浮  →  浮到水面 → 破掉（forgotten）
被想起  →  变重  →  下沉  →  想起来的次数越多，沉得越深
沉到最底 →  固化（consolidated）→ 重到浮不上来 → 再也忘不掉
         → 这就是「大脑皮层」
```

### 于是「潜入深处」有了意义

```
滚轮往下 → 相机穿过一层层泡沫（日常的、正在淡的、飘着的）
         → 越往下越安静、越少
         → 最后停在海床：十几颗围着一圈光环的星，一动不动

         「这就是她。」
```

**浅海是她的日常。海底是她这个人。**

潜入深处 = 看她真正的样子 = **亲密**，不是哀悼。

### 这条推翻了什么（诚实记录）

| 之前说过的 | 现在的结论 |
|---|---|
| **「沉下去 = 遗忘」** | ❌ **反了。** 沉 = 重要。遗忘是**上浮** |
| **「遗忘不移动，只磨损」** | ❌ 作废。**遗忘有一个动作：往上飘** |
| **「半径 = 权重」** | ❌ 改掉。半径只负责 tag 团内散开，不承载语义 |
| **「核 / 晕」分区** | ❌ 不需要。皮层自然聚在海底，**算出来的，不是摆出来的** |
| **「黑洞 = 忘了的记忆」** | ⚠️ 待定。重沉轻浮已经能表达「忘了」，黑洞可能多余 |
| **「删除角色 = 黑洞 / 数据损坏」** | ❌ 都作废。**用鲸落 + 墓碑**（见下） |

### 视觉通道的最终分配

| 通道 | 编码 | 备注 |
|---|---|---|
| **深度 z** | 重量 = 重要度 | **主通道** |
| **大小** | 重量 | 大石头同时也重 |
| **亮度** | 重量 | 沉的实，浮的虚 |
| **颜色** | 温度：海底冷白 · 水面暖橙 | **不表达亮度**，亮度单独管强度 |
| **光环** | 已固化 = 「落地了」 | 复用已有的髓鞘光环 |
| **x / y** | tag 团内散开 | 不承载语义 |

**三个通道说同一件事不是冗余** —— 真实世界里重的东西同时更大、更实、更沉。
用一个通道说，永远有点假。

### 缩放 = 焦距，不是筛选

```
缩小  全部可见，都小，能看到整片海的形状
放大  一层清楚，其他层还在，只是虚掉（alpha 衰减，不用真模糊）
```

**不能做成「只显示区间内的东西」** —— 那样深海会变成空房间，
你就看不到「大部分都还在上面」了。

**「它们还在，只是看不清了」—— 这句话本身就是生境的主题。**

### 死亡：鲸落，不是黑洞也不是乱码

```
角色被删 → 不是坍缩，不是乱码
         → 亮度停止闪烁（她连「活着」那个抖都没有了）
         → 开始往下沉，很慢，二三十秒
         → 沉到底，颜色一路冷下去
         → 它还在那儿。不发光，但没消失
         → 很久以后，那个位置出现一颗很小的新星（下一代）
```

**鲸落 = 一条鲸死后喂养一整个生态系统几十年。**
而 `graves` / `generation` 已经在算「她是第几代」了。

**为什么不黑洞**：黑洞是奇观，你会盯着看。
**为什么不乱码**：赛博朋克式的乱码是美学，你会想录屏。
**一块碑什么都不做，它让你安静。** 而这块软件是关于失去的。

### 潜意识闪回的画面

`residueHit` 那个概率闸（D-031：权重 0.13 → 42% 会醒）现在长这样：

```
一颗星正在慢慢上浮 —— 快浮出水面了
你说了那个词
      ↓
它突然变重（亮度闪一下）→ 往下沉了一截
      ↓
但不是每次都成功 —— 58% 的时候它只是晃一下，继续上浮
```

**「晃了一下又飘走」比「没反应」更像人。**

### 为什么这件事值得做

现在的记忆只有一种看法：**一张列表**。

```
· 他说以后一定先跟我说一声      长期   0.62
· 他受不了香菜的味道            偏好   0.41
· 那天海面很安静                情绪   0.18
```

列表只回答「有什么」，**不回答「她是怎么忘的」**。

而这个软件的整个设定是「关于失去」。**失去在列表里是看不见的** ——
一条 `0.62` 的变成 `0.18`，只是一个数字变了。

星图能让人**看见**一条记忆暗下去。

```
●  亮着的                 她记得
◐  暗了一半               想起来要费点劲
○  快灭了                 只有在特定的词上才回来
·  熄了                   想不起来了
```

**这是这个软件唯一能把「遗忘」画出来的地方。**

### 数据已经够用了 —— 一条新存储都不用加

`Memory` 现有字段直接映射成视觉维度：

| 字段 | 视觉 |
|---|---|
| `effectiveWeight(m)` | **亮度**。这是核心，是整张图的心跳 |
| `accessCount` | **光晕大小**。被想起来越多次，星越大 |
| `consolidated` | **颜色**。皮层 = 蓝白（冷、稳定）；海马体 = 暖橙（新、不稳） |
| `tag`（长期/短期/情绪/偏好） | **星座归属**。同 tag 聚成一团 |
| `lastAccessed` | **轨道半径**。越久没想起，离中心越远 |
| `forgotten` | **熄灭**。不再发光，只剩一个暗点 |
| `fromTimeShift` | **一圈淡紫的环** —— 提醒「这条是在拨表状态下产生的」 |
| `conv` | **哪颗大脑**。切换角色 = 换一片星域 |

**没有一项需要新字段。** 这是一次纯粹的「把已经存在的东西显示出来」。

### 四条视觉规则

**① 亮度会自己变**

不是快照。每天打开，星图都不一样 —— 因为她真的在忘。
**这条是全部意义所在。** 如果亮度是静态的，这图就只是一张装饰画。

**② 星团按 tag 分，但不硬分**

长期 / 短期 / 情绪 / 偏好 —— 四片星域。
但 `consolidated` 的星会从海马体那侧**飘向**皮层那侧。
**迁移是能看见的** —— 那是一条缓慢的弧线，不是一次跳变。

**③ 遗忘是熄灯，不是删除**

`forgotten` 的星不消失，变成暗点。
**星系不该被清理干净。** 一片空荡荡的星图没有故事。

**④ 点击一颗星，看得见它的过去**

```
「他受不了香菜的味道」
─────────────────
0.41  ◐  想起来过 3 次
上次：11 天前
状态：海马体 → 还没进皮层
```

以及一条**衰减曲线** —— 这个小图比任何文字都更能说明她是怎么忘的。

### 神经元化 —— 从「星图」升级到「神经元网络」

> **2026-11-03 补充。样张已做：`D:\Habitat_Archive\星图试验\memory-map-neuron.html`（已移出仓库）**

#### 为什么改名

原来的困境是「要不要连线」：

```
连线   → 蜘蛛网，那颗星被淹没
不连   → 没有「网感」
```

**而「神经元」这个词本身就给了答案：**

```
静息的神经元    不发光、不连线        ← 平时的星图
动作电位        放电，沿突触传出去     ← 被激活的那一瞬
```

**「平时不连、激活才连」不是折中，是正确模型。**

#### 三样已经做出来的（样张里有）

| 效果 | 实现 | 状态 |
|---|---|---|
| **髓鞘光环** | `consolidated` 的星外面一圈很淡的环，半径 ∝ 权重 | ✅ 已实现 |
| **点击脉冲** | 那颗星亮度 ×3.4，900ms 衰减，同时一个扩张环 | ✅ 已实现 |
| **突触闪现** | 0.72s 内，向相关的星闪细线，带沿线的亮头 | ✅ 已实现 |

**髓鞘光环比原来的「冷白」准**：

```
冷白      = 「这颗粒子温度不同」      视觉层
髓鞘光环   = 「这条路已经包了绝缘层」   结构层
```

髓鞘的功能就是**让信号传得更快更稳** —— 那正好是「反复想起之后忘不掉」的物理对应。

#### 突触连谁 —— 只用两条免费且真实的信号

| 信号 | 依据 | 成本 |
|---|---|---|
| **同一天 + 同 tag** | 同一个场景里发生的事 | 0 |
| **同实词** | 双字词命中 ≥ 2（剔停用字） | 0，用现成的 `resonates()` |

**❌ 「只有 tag 相同」不算关联。** 两条「偏好」之间没有突触，那只是同一个抽屉。
连上去等于把抽屉当神经。

**每条最多留 5 条突触** —— 实测 178 颗星平均 4.83 条，点一次闪 5 条线，不是毛球。

#### 技术选择：两张画布叠在一起

```
┌─────────────────────────────┐
│  <canvas class="ov">         │  普通 2D canvas：髓鞘环 + 突触线
├─────────────────────────────┤
│  <canvas class="gl">         │  three.js（WebGL）：星 + 中心
└─────────────────────────────┘
```

**为什么线不画在 three.js 里：**

| | three.js | 2D 上层 |
|---|---|---|
| 线条粗细 | ⚠️ **`linewidth` 在多数平台被忽略，永远 1px** | ✅ 想多粗多粗 |
| 渐变 / 沿线亮头 | 要写 vertex shader + 传时间 uniform | ✅ 两行 |
| 透视变细 | ✅ 自动 | ❌ 永远一样粗 |
| 被星遮挡 | ✅ 会 | ❌ 永远在最上层 |

**主因是第一条** —— WebGL 里画不出粗线，而突触必须带渐变和亮头。

**几何上是对的**：三维直线投影后仍是直线，所以两端各投影一次再连，透视完全正确。
不对的只有「线宽不随距离变细」和「不会被遮挡」——
**对于一个 0.7 秒就消失的闪光，这两点看不出来。**

**什么时候该搬进 three.js**：如果突触要变成**常驻的神经纤维**（粗、有体积、随镜头变细），
那就得用 `LineSegments` + 自定义 shader，或者 `TubeGeometry`。现在不值得。

#### 还没做的

| 项 | 为什么没做 |
|---|---|
| **回忆闪回的光束** —— `residueHit` 注入时，那颗星向聊天框射一条光 | **跨组件**：星图和聊天区要共享一条事件流，且得同时可见 |
| **真正的记忆数据接入** | 现在样张全是假数据，`Memory` 字段够用但还没接 |
| **`fromTimeShift` 的淡紫环** | 数据有，视觉还没做 |

#### 我们自己的东西 —— 这四件别人没有

**别人做的是「一个知识库的星图」。生境要做的是「一个角色的内心」。差别不在视觉，在立场。**

**① 这不是你的知识库，是她的脑子**

```
别人：你看你自己的知识库 —— 你在管理
我们：你在偷看她记住了什么 —— 你在窥视
```

同一种图，两种关系。**这个差别决定了所有文案的语气**：
不能写「共 288 个节点」，要写「她记得 288 件事」。

**② 遗忘是剧情，不是缺陷**

别人的遗忘曲线是**优化目标** —— 让它别忘。
我们的曲线是**看着它掉下去**。

```
别人：怎么让她记得更牢
我们：怎么让她忘得可信
```

**所以我们的曲线不该有「建议」「优化」这类词。它是一份病历，不是一份体检报告。**

**③ 有好几颗脑子 —— 这是最独有的一条**

群聊里有 3 个角色，就是 **3 张星图**。

```
同一件事：  鲸鲸 记在心里（亮）
            澜汐 早就忘了（紫）
            砂砾 从来没记住（根本没有那颗星）
```

**这个画面别人做不出来** —— 因为它需要「多个角色各有独立记忆」这个前提，
而绝大多数记忆系统是**单用户单库**。

**这一条是「多智能体社交」这个设定真正兑现的地方。**

**④ 想起来是概率的，不是检索**

我们的 `residueHit` 带概率闸（D-031）：提到那个词，**她可能想起来，也可能想不起来**。

别人的图是「点一下 → 查到」。我们的是「说到那件事 → 她愣一下 → 也许想起来」。

**这在视觉上应该是不一样的** —— 闪回不该是确定的光芒，是**迟疑之后才亮**。

#### 收敛成一句话

> 别人的星图回答「我有多少知识」。
> **生境的星图回答「她记得我多少，以及她正在忘掉哪些」。**

**所有设计决定都回到这句话上做判断。**

### 「生境化」的四个独家设计

> **2026-11-03 补。核心问题是：别做得像别人的东西。**

别人的图是**仪表盘**。我们要做的是**残缺的观测站**。
下面四条按「现在能不能做」排序 —— **不是按好不好**。

---

#### ⭐⭐⭐ 一 · 记忆的扭曲，不是检索

**这是四条里最好的一个。**

```
别人的星图：精准检索 —— 找得到
我们的星图：记忆会歪 —— 记得，但记得不对
```

**做法**：权重低的记忆，注入 prompt 时**改写讲法**，不是改内容。

```ts
// weight 高：  「那天我们在楼下吃了泡面」
// weight 低：  「那天吃了什么我记不清了，只记得挺开心的」
```

**⭐ 这里有一条不能越的线：**

```
❌ 编造事实   「那天吃的是炒饭」        ← 她说了没发生过的事
✅ 承认模糊   「吃了什么我记不清了」     ← 她记得自己忘了
```

**模糊的是「讲法」，不是「内容」。**

理由：编造会让用户发现「她说错了」，那是 bug。
承认模糊会让用户知道「她真的在忘」，那是剧情。

**实现落点**：`memoriesForPrompt()` 里，按 `effectiveWeight` 分档给记忆加前缀/修饰。
**不用改存储**，只改注入时的措辞。

**风险**：会不会有人为了看黑洞而去删角色？
不会 —— 删除不可逆，而且她真的就没了。**代价太高，不会有人试探。**

### 往后：记忆 / 语言 / 视觉 —— 三样东西，一条衰减

> **2026-11-03 补。看到大肥鱼分了三个子系统，想清楚了一件事。**

#### 不走「三个面板」的路

别人的做法：

```
记忆面板 / 语言面板 / 视觉面板
三个独立模块，各一套逻辑，各一块 UI
```

**我们不走这条。** 因为三个面板加起来就是「驾驶舱」，而我们要的是「深海」。

#### 真正可以独家的：三样东西活在同一个衰减场里

```
记忆  = 星本体        亮度 = effectiveWeight
语言  = 星之间的突触   粗细 = 用得多不多
视觉  = 带标记的星    「这颗曾经是张图」
```

**它们的共同点是「都会衰减」** —— 所以它们本来就在同一张图上，
不需要三块 UI，只需要三种**形态**。

#### 语言 = 突触 —— 这条几乎完美对上

黑话是什么？**是同一批记忆之间反复走的通路。**

```
新词冒出来    → 几条很弱的突触
群里确认过    → 突触变粗、变亮
没人再用了    → 突触变淡、消失
```

**这就是髓鞘化在人造概念上的应用。** 而「髓鞘」那套代码已经写好了 ——
现在用在 `consolidated` 记忆上，换到黑话上机制完全一样。

**生境独有的那句话：**

> 词汇也会忘。
> 一个只有你们俩才懂的词，因为没人再说，就慢慢消失了。

别人做黑话是**扩充词汇量**。我们做黑话是**看着一段默契死去**。

#### 视觉 = 带标记的星

```
玩家发一张图  → 立刻解析成两三句文字 → 存成记忆
一周后她回忆  → 「我记得是张有点模糊的照片……」
```

在星图上它就是一颗普通的星，但带一个**「曾经是张图」的标记**（一个方框状的环）。

**注意那条不能越的线**（见「记忆的扭曲」一节）：
细节宁可说「记不清了」，**不要说错**。

#### 前提：两个数据源都还没有

| | 现在 | 缺什么 |
|---|---|---|
| **记忆** | ✅ 有 | —— |
| **语言** | ❌ 没有 | **黑话提取**：从群聊里捞高频词、确认、入库 |
| **视觉** | ❌ 没有 | **图片消息**：现在连上传入口都没有 |

**这两样都不是「顺手加一下」，各是一个子系统。**

#### 顺序

```
1. 记忆这张图做好（现在在做）
2. 语言 = 黑话 + 突触强化
3. 视觉 = 图片消息 + 文字化 + 标记
```

**反过来做会得到一堆没有数据的空壳。**

**而且第 1 步没做好之前，讨论 2 和 3 都只是想象** ——
星图现在还是假数据，先把真的接上。

### 三个必须先回答的问题

> **2026-11-03 已拍板。** 结论在每条下面。


**① 遗忘能不能撤销？**

`Memory.forgotten` 现在**是可恢复的**（"仍在列表里，可以恢复"）。

但放到星图上就有问题了：

```
能恢复 → 星图变成收藏夹 → 用户会开始「抢救」星星
        → 遗忘变成一种可以反悔的东西
        → 整个设定塌掉
```

**我的倾向：不能恢复。** 或者恢复需要代价。
**但这是产品决定，不是技术决定，得你定。**

**② 用户能不能改亮度？**

「手动提权」在列表时代是无害的（调个数字）。
在星图里就是**手动点亮一颗星** —— 那是另一种味道。

会不会有人为了「让图好看」而反复提权？
提权之后她还是真的记得吗，还是被摆成了记得的样子？

**③ 星图是给谁看的？**

- 给**用户**看 → 这是一个仪表盘，可能让人开始优化分数
- 给**她**看 → 那这张图得是「她眼里的自己」，不是数据

这两者的差别，决定整个 UI 的调子。

#### ✅ 拍板结论

**① 遗忘能不能撤销？**

> **不能撤销。** 但恢复需要代价：玩家看着一颗星要熄灭想捞回来，
> 不是鼠标点一下，必须**通过一段对话去唤醒它**（重新提起那件事）。

**「用陪伴对抗遗忘。」**

**⭐ 而且这条根本不用实现 —— 它已经是真的：**

```ts

for (const m of live) touchMemory(m.id);   // 注入 = 想起来了
```

`touchMemory` 刷新 `lastAccessed` → 遗忘曲线从今天重新开始。

**你现在跟她聊那件事，那条记忆就真的往回走了一点。**

```
✅ 机制早就有
❌ 缺的从来不是功能
✅ 缺的是「不要给它加一个恢复按钮」
```

**这条的工程含义是「不做什么」，不是「做什么」。**
每次想加一个「恢复」按钮的时候，回来读一遍这句。

**② 用户能不能手动改亮度？**

> **可以改，但视觉上叫「强行唤起」。** 点提权，星会瞬间亮一下，
> 然后产生**不稳定的频闪** —— 提醒玩家：这是你强行摆出来的样子，
> 不是她自然想起来的。

**⚠️「频闪」这个词不够具体，不写清会被当成 bug。建议规格：**

```
强行唤起那一刻    瞬间亮到 0.9，0.35 秒内掉回
之后 3 秒内       亮度在两值之间「不规律」跳 4–6 次，幅度递减
3 秒后            稳定在「比原来略高」的值
```

**「不规律的抖」和「规律的闪」是两种东西：**

```
规律  = 加载中   → 像 bug
不规律 = 手在抖   → 像不安
```

**③ 星图是给谁看的？**

> **给玩家看，但视角是「偷看她的大脑」。**
> 所有文案都要用第三人称。
> 玩家不是在管理知识库，是在看一个活生生的灵魂在流失。

**和前面「我们自己的东西 ①」是同一条结论。** 两边独立想到了 → 这条稳。

**落在文案上：**

❌ 记忆健康度 99%        ✅ 大部分还清楚
❌ 优化建议              （没有这个词，永远不要加）
```

### 对生境的影响：现在为零

生境发的是**格式**，不是"调 OpenAI"：

```
POST /v1/audio/speech
{ model, input, voice, response_format }
```

**这不是"调 OpenAI"，这是"说一种普通话"。谁听得懂就发给谁。**

2027 年 OpenAI 不听了 —— 还有六家在听：

| doteb | ✅ 转 ElevenLabs / Gemini |

**有人在赌「OpenAI 格式会成为事实标准，而 OpenAI 自己不做了」。**

### 什么时候该动

**不是按日期动，是按条件动。**

- [ ] **如果 2027 年之后还有 ≥1 家服务支持 `/v1/audio/speech`** → **不动**
- [ ] **如果全部服务商都迁到 Realtime（WebSocket）** → **加一条流式通道**

**判断方法**：每年 12 月查一次 OpenAI 的 deprecations 页 + 上面那六家的文档。

### 到时候的三条路

**① 换一家还在支持的**（最省事）
```
只改默认 Base URL 和模型名。代码不动。
```

**② 加 Realtime 通道**（工作量大）
```
WebSocket + 流式音频解码。
好处是延迟从 2 秒降到 200 毫秒 —— 那才是"她在说话"的感觉。
坏处是整条播放链路要重写。
```

**③ 退回系统语音**（兜底）
```
native 那一档永远在。声音机械，但不会因为任何服务商的政策而死。
```

**这也是为什么当初做 `native` 是对的** ——
**它是唯一一个不受任何第三方政策影响的档位。**

### 现在不要做的

- ❌ **改默认模型名** —— `tts-1` 还能用到 2027-01-06。改成别人不认的名字反而会坏
- ❌ **现在写 Realtime 支持** —— 一年多以后的事，现在做是猜

## 六 · 主题层（换肤的地基）

> **2026-11-08 立。** 起因：打算让另一个模型重做整个 UI，
> 目标是「换肤 / 换主题，不动底层逻辑」。
> 它读完项目说「没有独立的主题层」—— 这话对了一半，我把实际情况量了一遍。

### 现状（实测数字，不是印象）

```
@theme 里已有         11 个颜色 token + 2 个字体      ✅ 存在
已经在用 token        710 处（text-biolum 这类）      ✅ 77%
硬编码颜色            207 处                          ⚠️
  · Tailwind 任意值     7 处   text-[#35f0ce]
  · 内联 style         54 处   style={{ color: '#…' }}
  · JS 对象           104 处   { accent: "#35f0ce" }   ← 大头
```

**最常用的 6 个颜色占了 135 / 207**，且全在 @theme 里有对应 token
（`#35f0ce`→biolum 59 次、`#ff7a6b`→coral 39 次、`#8fa9bd`→mist 10 次、
`#4e8cff`→tide 10 次、`#8b6bff`→lumen 9 次、`#ffc46b`→amber 8 次）。
剩 72 处是零散色，要逐个判断是并入现有 token 还是新增。

### 那条「只改 styles.css 就够」的判断，为什么不够

104 处颜色是**运行时传进组件的 JS 值**，CSS 变量覆盖不到：

```jsx
<Toast accent="#35f0ce" />
<span style={{ color: "#ff7a6b" }}>
```

只改 @theme 会「换一半，剩一半没换」—— 而没换的恰好是最显眼的
提示条强调色、角色头像色、系统条颜色。比不换更难看。

### 形状和布局能改多少（也量过了）

| 想改的 | 只改 CSS | 机制 | 规模 |
|---|---|---|---|
| 颜色 | ✅ 100% | `--color-*`（接完 207 处后） | 全部 |
| **圆角** | ✅ | `--radius-sm/md/lg/xl` | **355 处** |
| **间距 / 密度** | ✅ | `--spacing` 基准值，改一个数全部等比 | **1488 处**（p-* 1276 + gap-* 212）|
| 字号 | ✅ | `--text-*` | 大部分 |
| 面板质感 | ✅ | `.glass`（20 处）+ `backdrop-filter` | 部分 |
| `w-/h-` | ⚠️ 一半 | 用 spacing 的能变，`w-[320px]` 的不能 | 169 处 |
| **布局** | ❌ | `flex/grid/order-*` 是结构 | **140 处，集中在 4 个文件** |

**但三条栏是个例外 —— 它们的位置早就写在 CSS 里了：**

```css
.rail-console  { width: 15%; min-width: 176px; }
.rail-contacts { width: 20%; min-width: 208px; }
.rail-god      { width: 20%; min-width: 238px; }
@media (max-width: 1120px) { .rail-console { display: none } }
```

而且 `App.tsx:3404` 是 `<aside className={"..." + r.cls}>` 用 `.map()` 渲染的 ——
**是 flex 子元素，所以 `order:` 能重排，`display:none` 能藏。**

结论：**换肤能改「每个栏多宽、在哪、要不要」，不能改「栏内部长什么样」。**

### 三档「彻头彻尾」

| 档 | 能力 | 成本 | 风险 |
|---|---|---|---|
| **一 · 换皮** | 色 · 圆角 · 密度 · 字号 · 栏宽/顺序/显隐 | 半天 | 0 |
| **二 · 换结构** | 栏变抽屉 · 加第四栏 · 对话区上下分栏 | 改 `rails` 数组 + 状态 | 低 |
| **三 · 换骨架** | 任意组件可被主题替换（时间轴代替消息列表、头像墙代替左栏） | **~150 行基础设施** | 中（新机制，不动现有代码） |

**「想怎么改就怎么改」= 第三档。**

### 第三档的具体形状（还没做，先记着）

```
src/theme/
  tokens.css        @theme：色 / 圆角 / 间距 / 字号
  registry.ts       组件槽位表
  Theme.tsx         Provider + useTheme()

themes/default/     现在的实现（不动）
themes/<名字>/       主题只写自己想改的
```

主题清单：
```ts
export default {
  name: "琥珀",
  tokens: { "--color-biolum": "#ffc46b", "--radius-lg": "2px" },
  rails: { order: ["god", "contacts", "console"], hidden: [] },
  components: { MessageRow: AmberMessageRow },   // 只覆盖想改的
};
```

**唯一要小心的：每个槽位必须有 default 实现** ——
主题只覆盖它想改的，没覆盖的走 default，否则会因为没有实现而崩。
而且 **props 契约要冻结** —— 一旦变了，所有主题都得跟着改。

### 不做

- **亮色主题** —— 710 处 class 里有大量 `bg-white/[0.03]`、`text-ink/92`
  这种「按暗底设计」的写法，换浅底会白叠白看不见。
  那是逐个组件重调，不属于换肤范围。
